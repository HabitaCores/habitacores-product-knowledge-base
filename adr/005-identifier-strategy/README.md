## 1. Context

Habitacores will manage authoritative records across:

- Identity
- organizations
- memberships
- properties
- communities
- buildings
- blocks
- floors
- units
- listings
- inquiries
- inspections
- applications
- decisions
- charges
- payments
- allocations
- receipts
- agreements
- signatures
- occupancies
- maintenance
- work orders
- documents
- communications
- support sessions
- audit events
- outbox events
- integrations
- Responsible AI operations

The system requires identifiers that:

- Remain globally unique
- work across web and worker processes
- support future distributed generation
- preserve stable references when names change
- avoid dependence on one database sequence
- avoid exposing predictable record counts
- work naturally with PostgreSQL
- support event and idempotency workflows
- remain safe across organizations
- provide practical index locality
- remain separate from public business references
- support future expansion without re-keying core tables

ADR-004 selected PostgreSQL, Drizzle ORM, Drizzle Kit, and explicit repository boundaries.

ADR-005 must determine how Habitacores identifies records across the domain, database, APIs, events, URLs, integrations, logs, and user-facing workflows.

## 2. Decision Drivers

The decision is driven by the need to:

1. Provide globally unique identifiers.
2. support server-side generation before persistence.
3. support multiple runtime processes.
4. support future service extraction.
5. avoid central sequence coordination.
6. provide better insertion locality than fully random UUIDs.
7. preserve PostgreSQL’s native UUID storage.
8. prevent mutable business meaning from entering primary keys.
9. distinguish internal identity from human-readable references.
10. distinguish internal identity from provider identifiers.
11. support type-safe domain code.
12. support idempotency and event correlation.
13. avoid identifier enumeration as a product-information leak.
14. avoid treating opacity as authorization.
15. preserve unknown and pending business data accurately.
16. support data import without adopting external identifiers as primary keys.
17. support secure logs and audit references.
18. provide deterministic testing where required.
19. provide clear implementation boundaries for Codex.
20. avoid future large-scale primary-key migration.

## 3. Decision

Habitacores will use UUID version 7 as the default identifier for new authoritative domain entities.

The approved model is:

```text
Authoritative internal identifier:
UUIDv7

PostgreSQL column type:
uuid

TypeScript representation:
Branded domain-specific string type

Generation:
Trusted server-side identifier service

Database default:
Permitted where PostgreSQL support and migration policy approve it

Client generation:
Not trusted as authoritative by default

Human-readable reference:
Separate field

External provider identifier:
Separate field

Authorization:
Always evaluated independently of identifier possession
````

## 4. UUIDv7

UUIDv7 combines:

* A Unix timestamp in milliseconds
* UUID version and variant bits
* randomized remaining bits

Habitacores selects UUIDv7 because it provides:

* Standards-based representation
* global uniqueness
* chronological ordering characteristics
* improved index locality compared with random UUIDv4
* compatibility with PostgreSQL’s native `uuid` type
* generation outside a central sequence
* compatibility with future distributed processes
* familiar canonical textual formatting

## 5. PostgreSQL Representation

Authoritative identifiers will use:

```sql
uuid
```

They must not normally be stored as:

```text
varchar(36)
text
bytea
numeric
```

The PostgreSQL `uuid` type provides validation and compact native storage.

## 6. Generation Authority

Identifiers must be generated by trusted server-side infrastructure.

Approved generation locations may include:

* Application services
* domain factories through an injected identifier service
* deterministic workers
* AI workers for AI-operation records only
* PostgreSQL defaults where explicitly approved
* migration or import tooling

Browser-supplied identifiers must not automatically become authoritative entity identifiers.

## 7. Application-Side Generation

Application-side generation is preferred when an identifier is required before persistence.

Examples:

* Creating an aggregate and related outbox event
* constructing a command result
* correlating records across one transaction
* preparing an idempotent job
* creating an event envelope
* deterministic testing through an injected generator
* future service or offline workflow composition

Generation must use an approved RFC-compliant UUIDv7 implementation.

The exact library will be selected during implementation and pinned under ADR-003 dependency controls.

## 8. Database-Side Generation

PostgreSQL-native UUIDv7 generation may be used when:

* The approved PostgreSQL version supports it.
* the identifier is not needed before insertion.
* schema defaults improve safety.
* repository behavior remains predictable.
* generated values are returned reliably.
* tests cover the behavior.
* migrations explicitly define the default.

Database defaults must not create inconsistent generation rules across similar entities.

## 9. Generation Consistency

Habitacores will establish one identifier-generation abstraction.

Conceptual interface:

```typescript
interface IdentifierGenerator {
  next(): string;
}
```

Domain-specific factories should wrap the generic generator rather than expose raw identifier creation everywhere.

The architecture must avoid:

* One module using UUIDv4
* another using UUIDv7
* another using ULID
* another using database sequences
* another accepting browser-generated identifiers

without an approved exception.

## 10. Branded Domain Types

Raw strings must not be interchangeable across domain identifiers.

Illustrative TypeScript model:

```typescript
declare const organizationIdBrand: unique symbol;
declare const propertyIdBrand: unique symbol;
declare const applicationIdBrand: unique symbol;

export type OrganizationId =
  string & { readonly [organizationIdBrand]: true };

export type PropertyId =
  string & { readonly [propertyIdBrand]: true };

export type ApplicationId =
  string & { readonly [applicationIdBrand]: true };
```

This reduces accidental substitution such as passing a property identifier where an organization identifier is required.

## 11. Identifier Constructors

Each branded identifier should be constructed through validated functions.

Illustrative:

```typescript
function parseOrganizationId(value: string): OrganizationId;
function createOrganizationId(
  generator: IdentifierGenerator
): OrganizationId;
```

Constructors should verify:

* Canonical UUID syntax
* approved version where required
* nonempty value
* expected domain type at the API boundary

Database migration imports may require controlled compatibility with historical UUID versions.

## 12. Canonical Text Format

UUIDs should be serialized in canonical lowercase hyphenated format.

Example:

```text
0198f181-8df0-7a44-b7df-87a749f01517
```

The system should accept only deliberately supported input formats at API boundaries and normalize them before use.

Case differences must not create distinct logical identifiers.

## 13. Primary Keys

New authoritative tables should normally use:

```sql
id uuid primary key
```

A table may use a composite primary key only when the relationship itself is the authoritative identity and the decision is deliberate.

Composite uniqueness may still be used alongside a UUID primary key.

## 14. Foreign Keys

Foreign keys must use the same PostgreSQL `uuid` representation as the referenced primary key.

Examples:

```text
organization_id
property_id
application_id
agreement_id
occupancy_id
```

Foreign-key columns must not use text while the referenced key uses `uuid`.

## 15. Stable Identity

An identifier must remain stable when:

* A person changes their name
* an organization changes its display name
* a building is rebranded
* Block A or Block B receives a public name
* a unit reference changes
* a listing title changes
* an agreement receives a new document version
* a maintenance ticket changes status
* a public-facing reference is reformatted

Mutable display values must not become primary keys.

## 16. No Business Meaning in Primary Keys

Primary identifiers must not encode:

* Organization name
* property name
* state
* city
* building name
* role
* year
* status
* currency
* unit count
* agreement status
* payment status
* document classification

An identifier must not require replacement when a business fact changes.

## 17. Human-Readable References

Human-facing workflows may use separate references.

Examples:

```text
Application:
APP-2026-000184

Receipt:
RCT-2026-000421

Agreement:
AGR-2026-000073

Maintenance:
MNT-2026-000512
```

These examples are illustrative only. Their exact format requires implementation design.

Human-readable references must not replace internal UUID primary keys.

## 18. Human-Readable Reference Requirements

A public or operational reference should be:

* Unique within its declared scope
* easy to read
* easy to communicate
* resistant to transcription ambiguity where practical
* generated server side
* immutable after issuance
* separate from authorization
* backed by a database uniqueness constraint

The scope may be:

* Global
* organization specific
* document-type specific
* year specific

The scope must be explicit.

## 19. Sequence Disclosure

Human-readable references may expose approximate issuance order.

Therefore:

* They should be introduced only where operational value justifies it.
* they must not reveal restricted aggregate counts unnecessarily.
* public references may use nonconsecutive or encoded sequences where justified.
* the internal UUID remains the authoritative identity.

## 20. Public URL Identifiers

Public or authenticated URLs may use UUID identifiers when appropriate.

Example:

```text
/applications/0198f181-8df0-7a44-b7df-87a749f01517
```

Possession of the URL does not grant access.

Every request must still enforce:

* Authentication where required
* organization context
* permission
* assignment
* resource ownership
* record state
* support-session context where applicable

## 21. Slugs

Slugs may be used for public discoverability and readability.

Examples:

```text
/properties/the-lakeside
/listings/three-bedroom-flat-katy-example
```

Slugs are not authoritative identifiers.

A slug must:

* Resolve to an internal identifier
* support uniqueness rules
* support controlled renaming
* avoid exposing private records
* preserve redirect history where required
* remain separate from tenant authorization

## 22. External Provider Identifiers

Provider identifiers must use dedicated fields.

Examples:

```text
payment_provider_customer_id
payment_provider_transaction_id
signature_provider_envelope_id
email_provider_message_id
storage_provider_object_key
ai_provider_request_id
```

Provider identifiers must not become Habitacores primary keys.

## 23. Provider Identifier Scope

Every provider identifier must include sufficient context to avoid ambiguity.

Relevant context may include:

* Provider
* provider account
* environment
* organization
* integration configuration
* resource type

A transaction identifier from one provider account or environment must not be assumed globally unique unless the provider contract guarantees it.

## 24. Environment Separation

Identifiers generated by Habitacores may be globally unique across environments, but environment boundaries remain explicit.

Production, staging, test, and local records must not be confused merely because identifiers share one format.

Provider references must always preserve provider environment context.

Logs and exports should identify the Habitacores environment independently of the record identifier.

## 25. Imported Records

Imported records will receive new Habitacores internal identifiers.

Legacy identifiers should be stored separately, for example:

```text
legacy_system
legacy_record_type
legacy_record_id
```

Imports must not adopt external identifiers as internal primary keys unless a separately approved migration requires it.

## 26. Import Idempotency

A unique mapping should prevent duplicate imports.

Potential uniqueness scope:

```text
organization_id
legacy_system
legacy_record_type
legacy_record_id
```

Re-running an import must not create duplicate entities when the same source record has already been mapped.

## 27. Event Identifiers

Every domain, integration, and outbox event must have a unique event identifier.

Event identifiers should use UUIDv7 unless a provider-supplied event identifier is being recorded separately.

An event envelope may contain:

```typescript
interface EventEnvelope<T> {
  eventId: EventId;
  eventType: string;
  eventVersion: number;
  occurredAt: Date;
  organizationId?: OrganizationId;
  resourceId?: string;
  correlationId: CorrelationId;
  causationId?: EventId;
  payload: T;
}
```

## 28. Correlation Identifiers

Correlation identifiers should use opaque generated identifiers.

UUIDv7 is approved for correlation IDs where one is generated internally.

A correlation ID:

* Links one workflow across processes
* does not replace resource identity
* does not provide authorization
* may appear in safe operational messages
* must not contain personal information
* should propagate into workers and provider adapters

## 29. Causation Identifiers

Events and jobs may preserve a causation identifier showing which prior event or command initiated them.

Causation identifiers must remain separate from:

* Event identifiers
* correlation identifiers
* resource identifiers
* idempotency keys

## 30. Idempotency Keys

Idempotency keys are not automatically entity identifiers.

They may be:

* Generated by Habitacores
* supplied by approved clients
* derived under a documented deterministic scheme

An idempotency record should preserve:

* Scope
* actor or integration
* organization
* operation
* key
* request fingerprint where appropriate
* result
* expiry or retention policy

Random UUIDv7 values may be used as generated idempotency keys, but the semantic distinction must remain clear.

## 31. Document Identity

A logical document and a document version require separate identities.

Example:

```text
Agreement:
agreement_id

Agreement version:
agreement_version_id
```

Issuing a revised document must not overwrite the identity of the prior immutable version.

Storage object keys must not substitute for document identifiers.

## 32. Person and Account Identity

The architecture must distinguish:

* User account
* person profile
* organization membership
* role assignment
* invitation
* authentication-provider subject

An authentication-provider subject identifier must not automatically become the primary key for all Habitacores identity records.

This separation supports:

* Provider replacement
* multiple identity links
* account recovery
* invitations
* membership history
* support operations

## 33. Property Hierarchy Identity

Each hierarchy level receives its own stable identifier:

```text
Organization
→ Property
→ Community
→ Building
→ Block
→ Floor
→ Unit
```

Display labels such as:

```text
Block A
Block B
First Floor
Unit 1
```

must not serve as globally authoritative identifiers.

## 34. Unit References

A unit may have:

* Internal UUID
* organization or property scoped operational reference
* display label
* historical labels

Changing a display label must not break:

* Agreements
* occupancy history
* payment records
* maintenance records
* documents
* audit history

## 35. Versioned Records

Version records must have independent identifiers.

Examples:

* Agreement version
* policy version
* prompt version
* model configuration version
* document version
* listing publication version

A version number such as `3` is not sufficient as a globally unique identity without the parent identifier.

## 36. Audit References

Audit events should reference:

* Resource type
* internal resource identifier
* organization identifier
* actor identifier
* correlation identifier
* support-session identifier where applicable

Audit metadata should not rely solely on mutable display labels.

## 37. Logging

Logs may contain internal identifiers where operationally necessary.

Logs must not automatically contain:

* Full identity-document numbers
* full bank references
* payment evidence contents
* signed-document contents
* provider secrets
* raw personal data

Identifiers in logs must still follow retention and access controls.

## 38. Identifier Enumeration

UUIDv7 values are opaque enough to avoid simple sequential enumeration, but they contain time-ordering information.

The architecture must not describe UUIDv7 as secret or unguessable authorization.

A user who obtains a valid identifier must still fail to access an unauthorized resource.

## 39. Timestamp Semantics

The timestamp portion of UUIDv7 indicates generation time characteristics.

It is not the authoritative business timestamp.

Every record requiring time semantics must maintain explicit fields such as:

```text
created_at
occurred_at
submitted_at
verified_at
effective_at
```

Business reports and legal decisions must not derive authoritative event time solely from a UUID.

## 40. Ordering

UUIDv7 may assist approximate creation ordering and index locality.

Queries requiring deterministic ordering must still use explicit ordering columns and tie breakers.

Example:

```text
ORDER BY created_at, id
```

Identifier ordering alone must not define business priority.

## 41. Clock Behavior

Identifier generation must tolerate practical clock irregularities without producing collisions.

The approved implementation must follow the selected library or database implementation’s RFC-compliant monotonicity behavior.

System clocks must be synchronized operationally.

A clock error must not silently become authoritative business time.

## 42. Collision Handling

UUID collision probability is extremely low, but database uniqueness remains authoritative.

All primary identifiers require:

```text
PRIMARY KEY
```

or an equivalent unique constraint.

A duplicate-key failure during generation should:

* Be treated as an exceptional conflict
* avoid overwriting an existing record
* regenerate only where safe
* preserve diagnostics
* avoid leaking unrelated record data

## 43. Identifier Validation

API and command boundaries must validate identifiers before database use.

Validation should reject:

* Empty values
* malformed values
* unsupported resource-reference formats
* values longer than expected
* mixed identifier and slug inputs without explicit routing
* provider references passed as internal identifiers

A syntactically valid UUID is not proof that the resource exists or is authorized.

## 44. API Representation

APIs will normally serialize UUID identifiers as strings.

Example:

```json
{
  "applicationId": "0198f181-8df0-7a44-b7df-87a749f01517"
}
```

Field names should identify the resource type rather than use ambiguous generic fields throughout nested contracts.

Preferred:

```text
organizationId
applicationId
agreementId
```

Avoid ambiguous use of:

```text
id
```

where several resource identifiers appear in one payload.

## 45. Database Defaults

Where a database default is approved, the schema should remain explicit.

Conceptual example:

```sql
id uuid primary key default uuidv7()
```

This specific function depends on the approved PostgreSQL version.

Where native generation is unavailable or not selected, the application must supply the UUIDv7.

## 46. No Mixed Default Without Reason

One table must not use application-generated UUIDv7 while an equivalent table uses database-generated UUIDv4 merely because of framework defaults.

Exceptions require documentation.

Migration-generated defaults must be reviewed to ensure the version matches the ADR.

## 47. Historical Compatibility

If preexisting records use another identifier version, they may remain valid in PostgreSQL `uuid` columns.

Habitacores should not rewrite stable historical identifiers merely to make all rows UUIDv7.

New-record generation must follow the approved current policy.

## 48. Legacy Numeric Identifiers

Legacy numeric IDs may be retained as source references where required.

They must not be exposed as authoritative Habitacores identity unless an approved migration plan explicitly adopts them.

The system may maintain:

```text
legacy_numeric_id
```

with a scoped uniqueness constraint.

## 49. Analytics and Warehousing

Downstream analytical systems should preserve internal identifiers as stable dimensions.

An analytical surrogate key may be added within the warehouse, but it must not replace the Habitacores source identifier in lineage.

Exports should clearly label:

* Internal identifier
* human-readable reference
* external provider reference
* legacy identifier

## 50. Responsible AI Identifiers

AI operations must have dedicated identifiers.

Potential records include:

* AI operation
* AI result
* evaluation run
* prompt version
* model configuration
* human review

AI identifiers must not gain authority over the business resource they reference.

An AI result identifier cannot be used as:

* Application decision ID
* payment verification ID
* agreement activation ID
* occupancy activation ID

unless a deterministic human-authorized domain record is created separately.

## 51. AI Source References

AI-generated content should reference approved source resources through stable internal identifiers and permitted document-version identifiers.

Source references must not expose:

* Another organization’s resources
* unrestricted storage keys
* provider secrets
* private internal paths

## 52. Security Boundary

Identifiers support record addressing.

They do not prove:

* Identity
* membership
* role
* permission
* assignment
* organization ownership
* support authority
* document access
* payment authority
* legal authority

Authorization remains mandatory at every protected boundary.

## 53. Client-Supplied Identifiers

Clients may supply identifiers when referring to existing resources.

The server must validate:

1. Syntax
2. existence
3. organization ownership
4. relationship
5. actor permission
6. record state
7. command eligibility

Client possession of an identifier does not satisfy any of these checks.

## 54. Client-Generated Draft Identifiers

Client-generated identifiers may be considered for offline or resilient draft workflows only through a separately approved design.

Such a design must address:

* Collision and version validation
* ownership
* replay
* idempotency
* malicious identifier substitution
* synchronization
* draft expiry
* authoritative acceptance

Client-generated IDs are not approved as a general MVP default.

## 55. Deletion and Reuse

An identifier must never be reassigned to another logical entity.

Deleted, archived, revoked, superseded, or merged records retain their historical identity.

Human-readable references should also not be reused where doing so would create audit, legal, or operational ambiguity.

## 56. Merge and Deduplication

When duplicate logical records are merged:

* Each original identifier remains traceable.
* one canonical record may be selected.
* redirects or mapping records may preserve lineage.
* audit records must explain the merge.
* foreign-key migration must be controlled.
* identifiers must not be silently reassigned.

## 57. Identifier Generation Package

Identifier infrastructure should reside in a stable shared package.

Potential path:

```text
packages/contracts/src/identifiers
```

or:

```text
packages/domain/src/identifiers
```

The exact location should preserve:

* Domain type ownership
* server-side generation
* testability
* no framework dependency
* no provider dependency

A separate top-level package is unnecessary unless the boundary becomes substantial.

## 58. Test Generators

Tests should use injected or deterministic identifier generators where repeatability matters.

Examples:

* Fixed sequence of valid UUIDv7 values
* seeded generator
* explicit fixture identifiers

Production generation must not become deterministic.

## 59. Test Fixtures

Fixture identifiers must:

* Be syntactically valid
* remain clearly synthetic
* preserve type distinctions
* avoid real production identifiers
* support organization-isolation tests

Cross-tenant tests should deliberately use valid identifiers belonging to another synthetic organization.

## 60. Migration Requirements

When adding an identified table, the migration must define:

* UUID column
* primary-key constraint
* generation default where approved
* foreign-key compatibility
* required uniqueness constraints
* indexes justified by query behavior

A migration must not silently use `serial`, `bigserial`, or `identity` for authoritative domain keys without an approved exception.

## 61. Drizzle Representation

Drizzle schema definitions must use the PostgreSQL UUID type.

Conceptual example:

```typescript
export const organizations = pgTable("organizations", {
  id: uuid("id").primaryKey(),
});
```

The exact default-generation expression depends on the approved generation location and PostgreSQL version.

## 62. Package Boundary

Domain packages may know branded identifiers.

They must not depend on:

* Drizzle
* PostgreSQL
* database-generation functions
* Next.js
* provider SDKs

Database infrastructure maps branded identifiers to PostgreSQL UUID columns.

## 63. API Compatibility

Changing identifier format in a published API is a breaking change.

Therefore:

* UUIDv7 should be selected before public API contracts stabilize.
* parsers must remain version aware.
* clients must treat identifiers as opaque strings.
* clients must not parse timestamp bits for business behavior.
* clients must not assume lexical order represents priority.

## 64. Human Reference Generation

Human-readable references may use controlled database sequences because their purpose differs from primary identity.

Any such sequence must define:

* Scope
* prefix
* padding
* reset behavior
* concurrency
* uniqueness
* gaps
* cancellation behavior
* privacy implications

Gapless numbering must not be promised unless a legal or accounting requirement explicitly demands it and the transactional cost is accepted.

## 65. Receipt References

Receipt identifiers may have statutory or accounting requirements.

The exact receipt-number architecture must be decided with the finance and compliance design.

The internal receipt record will still use UUIDv7.

## 66. Agreement References

Agreement references may combine:

* Organization code
* year
* controlled sequence

Such formatting remains a display and operational reference.

The agreement and each agreement version retain independent internal UUIDs.

## 67. Property References

Properties, buildings, blocks, floors, and units may receive scoped operational codes.

Examples:

```text
PROP-001
BLDG-A
BLOCK-A
UNIT-A-01
```

These remain mutable or supersedable operational labels according to policy.

They must not replace stable internal identity.

## 68. Pilot Property Neutrality

The identifier architecture must not assume:

* Every property has Block A
* every property has Block B
* every Block A has six units
* every community contains a masjid
* every second building has a water feature
* every unit uses one fixed naming pattern

The pilot’s display labels remain data, not identifier architecture.

## 69. Error Handling

Identifier errors should map to stable outcomes:

```text
INVALID_IDENTIFIER
RESOURCE_NOT_FOUND
RESOURCE_NOT_ACCESSIBLE
IDENTIFIER_CONFLICT
REFERENCE_ALREADY_EXISTS
EXTERNAL_REFERENCE_CONFLICT
```

Protected-resource handling may intentionally avoid distinguishing not-found from unauthorized where enumeration risk exists.

## 70. Observability

Identifier-related telemetry may include:

* Resource type
* operation
* internal identifier where permitted
* correlation identifier
* result code
* generation failure
* parsing failure
* duplicate conflict

Telemetry must not log unrestricted payloads merely because an identifier is present.

## 71. Codex Boundaries

Every Codex work package involving identifiers must specify:

* Entity type
* branded identifier type
* database representation
* generation location
* public reference requirement
* external reference requirement
* migration requirement
* API representation
* authorization expectations
* tests

Codex must not:

* Introduce numeric primary keys
* switch to UUIDv4
* introduce ULID
* encode business meaning in primary keys
* accept arbitrary browser IDs as authoritative
* use slugs as primary keys
* use provider IDs as internal keys
* treat UUID possession as authorization
* derive authoritative timestamps from UUIDs
* create inconsistent ID generators
* expose database sequences unintentionally

## 72. Prohibited Patterns

The following are not approved:

* `serial` or `bigserial` as the default domain-entity key
* auto-increment IDs exposed as the primary public resource reference
* UUID stored as unrestricted text
* browser-generated authoritative IDs by default
* mutable names used as primary keys
* provider IDs used as Habitacores primary keys
* one generic unbranded string type for all identifiers
* identifier secrecy used instead of authorization
* business timestamps derived solely from UUID timestamp bits
* random mixing of UUID versions
* changing existing identifiers after renaming
* reusing identifiers after deletion
* parsing identifier timestamp bits in client business logic

## 73. Options Considered

### Option A — Auto-Incrementing `bigint`

Advantages:

* Compact storage
* simple generation
* strong insertion locality
* familiar database behavior

Disadvantages:

* Requires centralized database sequence generation
* exposes predictable ordering and approximate counts
* less suitable for generation before persistence
* less convenient for future distributed processes
* increases coupling to one database authority
* more difficult to merge imported or independently generated records

Decision:

Rejected as the default authoritative identifier.

### Option B — UUIDv4

Advantages:

* Standardized
* broadly supported
* strong randomness
* native Node.js generation
* native PostgreSQL storage

Disadvantages:

* Random ordering
* poorer index locality than time-ordered alternatives
* lacks useful generation ordering
* offers no meaningful advantage over UUIDv7 for new Habitacores entities

Decision:

Rejected as the default for new records.

UUIDv4 may remain valid for external or historical identifiers.

### Option C — ULID

Advantages:

* Lexicographically sortable
* compact text form
* timestamp based
* commonly used in distributed systems

Disadvantages:

* Not PostgreSQL’s native UUID representation
* requires additional conventions and libraries
* case and canonicalization considerations
* less aligned with current standardized UUID infrastructure
* no material advantage sufficient to outweigh UUIDv7 interoperability

Decision:

Rejected.

### Option D — UUIDv7

Advantages:

* Standardized
* time ordered
* globally unique
* PostgreSQL UUID compatible
* suitable for generation before persistence
* better index locality than fully random UUIDs
* compatible with distributed expansion
* canonical familiar representation

Disadvantages:

* Reveals approximate generation time
* built-in Node.js UUID generation does not provide v7
* library or database support must be validated
* not a substitute for explicit timestamps
* monotonic behavior requires reliable implementation

Decision:

Approved.

### Option E — Dual Internal Numeric Key and Public UUID

Advantages:

* Compact internal joins
* opaque external IDs
* flexibility in public representation

Disadvantages:

* Two identities for every record
* additional indexes and mapping
* higher schema and developer complexity
* greater chance of using the wrong identifier
* little demonstrated MVP benefit

Decision:

Rejected as the default.

A specialized high-volume table may adopt a dual-key model only through evidence and review.

## 74. Positive Consequences

* Stable globally unique entity identity
* distributed generation capability
* improved index locality over UUIDv4
* native PostgreSQL UUID storage
* no central sequence dependency for core entities
* reduced simple enumeration
* clean separation between identity and display references
* clean separation from provider IDs
* stronger TypeScript type safety
* future application and service expansion without re-keying
* consistent event and correlation identifiers

## 75. Negative Consequences

* UUIDs are larger than bigint keys.
* text representations are less human friendly.
* Node.js requires an approved UUIDv7 implementation.
* timestamp characteristics may reveal approximate creation time.
* branded types require additional TypeScript utilities.
* human-facing workflows still require separate references.
* developers must preserve distinctions among resource, event, correlation, and idempotency identifiers.

## 77. Acceptance Criterion — New Entity

```text
Given:
A new organization is created.

When:
The application service constructs the organization.

Then:
A trusted server-side UUIDv7 identifier is assigned.

And:
The identifier is persisted in a PostgreSQL uuid primary-key column.

And:
The organization name is not encoded into the identifier.
```

## 78. Acceptance Criterion — Stable Rename

```text
Given:
A building is renamed.

When:
The display name changes.

Then:
The building identifier remains unchanged.

And:
Existing units, agreements, occupancies, maintenance records, and audit events continue referencing the same building.
```

## 79. Acceptance Criterion — Authorization

```text
Given:
A user from Organization A obtains a valid Organization B application identifier.

When:
The user requests the application.

Then:
The request is denied or safely treated as inaccessible.

And:
The syntactically valid identifier does not grant access.
```

## 80. Acceptance Criterion — Human Reference

```text
Given:
A rental application is submitted.

When:
The application receives an operational reference.

Then:
The internal UUIDv7 remains the primary identity.

And:
The human-readable application reference is stored separately.

And:
Both values have appropriate uniqueness constraints.
```

## 81. Acceptance Criterion — Provider Identifier

```text
Given:
A payment provider returns a transaction identifier.

Habitacores records the provider transaction.

Then:
The provider identifier is stored in a provider-scoped field.

And:
A Habitacores UUIDv7 identifies the internal payment record.

And:
The provider identifier does not become the primary key.
```

## 82. Acceptance Criterion — Event Identity

```text
Given:
An application submission creates an outbox event.

When:
The transaction commits.

Then:
The application and event each have distinct UUIDv7 identifiers.

And:
The event preserves the application resource identifier and correlation identifier separately.
```

## 83. Acceptance Criterion — Unknown Pilot Data

```text

Block B unit inventory remains unconfirmed.

When:
Identifiers are created for confirmed property hierarchy records.

Then:
No identifiers are generated for invented Block B units.

And:
Identifier generation does not imply that an unknown entity exists.
```

## 84. Acceptance Criterion — Imported Record

```text

A legacy property record is imported.

When:
Habitacores creates the property.

Then:
A new internal UUIDv7 is assigned.

And:
The legacy identifier is preserved in a separate scoped mapping.

And:
Re-running the import does not create a duplicate property.
```

## 85. Acceptance Criterion — Explicit Time

```text

A payment verification event has a UUIDv7 identifier.

The verification time is displayed or audited.
```

## 88. Supersession Conditions

This ADR should be reviewed when:

* UUIDv7 support proves operationally unsuitable.
* PostgreSQL identifier storage requirements change.
* distributed generation creates measurable collision or monotonicity concerns.
* database scale demonstrates a material UUID index limitation.
* legal requirements impose a different authoritative numbering system.
* public APIs require a materially different identifier architecture.
* offline-first clients require client-authoritative generation.
* a major data-platform migration requires re-keying.

## 89. Final Decision Statement

Habitacores will use UUIDv7 as the default identifier for new authoritative domain entities, events, jobs, and internally generated correlation records.

Identifiers will be stored using PostgreSQL’s native `uuid` type and represented in application code through validated domain-specific branded types.

Trusted server-side infrastructure will generate authoritative identifiers. Application-side generation is preferred where identity is required before persistence. PostgreSQL-side UUIDv7 defaults may be used where the approved database version supports them and the schema policy explicitly selects them.

Human-readable operational references, slugs, legacy identifiers, storage keys, authentication-provider subjects, and external-provider identifiers will remain separate from internal primary keys.

UUID timestamp characteristics will not replace explicit business timestamps. Identifier possession will never replace authentication, organization resolution, authorization, assignment validation, resource-state validation, or support-session control.

Names, labels, statuses, tenant information, locations, years, currencies, provider details, or other mutable business meaning will not be encoded into authoritative primary keys.

No browser, framework default, ORM, database migration, provider, worker, AI process, coding agent, import, public URL, human-readable reference, slug, sequence, or external identifier may silently redefine authoritative Habitacores identity or bypass its tenant-isolation, authorization, audit, financial, agreement, occupancy, document-security, or Responsible AI controls.
